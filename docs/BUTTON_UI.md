# راهنمای رابط دکمه‌محور

## کاربری روزانه

پس از `/start` مشتری شش دکمه در پنج ردیف اصلیِ سند می‌بیند: فروشگاه؛ کیف پول و حساب من؛ پشتیبانی؛ دعوت و کسب درآمد؛ کانال. رنگ، ترتیب و لینک مستقیم کانال تغییر نکرده‌اند. فقط مدیر فعال با chat ID اثبات‌شده یک ردیف «پنل مدیریت» نیز دارد. انتخاب آن وارد پنل ۱۳بخشی و متناسب با نقش می‌شود. منوی فرمان‌های Telegram فقط start را معرفی می‌کند؛ فرمان‌های قبلی حذف نشده‌اند و مسیر اختیاری سازگاری‌اند.

۱. بخش، سپس عملیات را انتخاب کنید.
۲. نوع، وضعیت، محصول، دسته، کاربر، سفارش و رکوردها را با دکمه انتخاب کنید. انتخابگر رکورد جست‌وجوی متنی، total دقیق و صفحات ۲۰تایی دارد. عبارت جست‌وجو رکورد را اجرا نمی‌کند؛ نتیجه باید با دکمه انتخاب شود.
۳. تنها داده‌های آزاد مانند نام، مبلغ، شرح، متن یا مشخصات مدیر جدید را تایپ کنید. برای مدیر جدید هم یوزرنیم و هم چت‌آی‌دی لازم است. اطلاعات ناشناخته تا اثبات همان هویت دسترسی ایجاد نمی‌کند.
۴. تاریخ را از گزینه‌های آماده یا به قالب میلادی YYYY-MM-DD وارد کنید. «همه / بدون محدودیت» فقط در فیلد اختیاری نمایش داده می‌شود. روزهای یادآوری صفر و بالاترند. محصولات شرط ترکیبی چندانتخابی‌اند؛ کاربر JSON نمی‌نویسد.
۵. پیش از ۵۴ عملیات تغییردهنده، خلاصه و «تأیید و اجرا» نمایش داده می‌شود. متن بلند صرفاً در پیش‌نمایش کوتاه می‌شود، نه در داده اصلی. اطلاعات محرمانه انبار و تحویل در خلاصه بازنشر نمی‌شود. محدودیت امن تحویل همچنان پیش از mutation اعتبارسنجی می‌شود.
۶. «مرحله قبل / اصلاح» پاسخ همان مرحله و مراحل وابسته بعدی را پاک می‌کند. «لغو و بازگشت» هیچ mutation تازه‌ای اجرا نمی‌کند. این لغو، تراکنش قبلاً انجام‌شده را برنمی‌گرداند.
۷. پس از مشاهده کاربر، سفارش، تیکت یا پرداخت، عملیات مرتبط نیز به‌صورت دکمه نمایش داده می‌شوند. navigation فهرست‌ها فیلتر را حفظ می‌کند. برای پیام گروهی، پیش‌نمایش واقعی تعداد مخاطب و تأیید پایدار قبلی حفظ شده است.

۸. پس از ادامه، پایان یا لغو، دکمه‌های پیام مرحلهٔ قبلی در صورت موفقیت Telegram غیرفعال می‌شوند؛ خود پیام حذف نمی‌شود. لمس دکمهٔ کش‌شده/قدیمی عملیات را دوباره اجرا نمی‌کند: فرم فعلی بازنمایی می‌شود یا اگر پایان یافته، دکمه‌های ادامه و «نمایش دوباره نتیجه» برای فهرست خواندنی نشان داده می‌شوند. فیلتر و صفحهٔ فهرست حفظ می‌شوند. نقش لغوشده هیچ فرم محرمانه‌ای را بازیابی نمی‌کند.

فرم‌های نام، شارژ، تخفیف، فیش، اطلاعات سفارش و تیکتِ مشتری دکمه خروج دارند. تماس همچنان فقط با دکمه رسمی ارسال شماره متعلق به خود کاربر پذیرفته می‌شود. لغو ورود اطلاعات، سفارش یا پرداخت موجود را لغو نمی‌کند؛ برای آن باید از عملیات اختصاصی خود سفارش/پرداخت استفاده شود. در مرحله تخفیف نیز بازگشت به منوی اصلی state را پاک می‌کند؛ سفارش از حساب من قابل ادامه است.

## دسترسی و سازگاری

در ورودی‌های متنی مشتری، صفحه‌کلید قبلی با دکمه «لغو و بازگشت» جایگزین می‌شود تا عنوان دکمه منوی قبلی تصادفاً به‌عنوان نام یا شرح ثبت نشود. برای تکمیل دستی مدیر می‌تواند دکمه متن پیش‌فرض همان محصول را انتخاب کند یا متن تحویل سفارشی بفرستد؛ هر دو مسیر تأیید نهایی دارند.

مالک همه بخش‌ها را دارد. مدیر می‌تواند مدیر و پشتیبان اضافه کند اما حق ارتقا به owner یا تغییر owner را ندارد. بکاپ کامل و تعیین تکلیف review مالی فقط برای owner است. پشتیبان تنها عملیات تعریف‌شده در SUPPORT_COMMANDS را دارد: مشاهده کاربر و تاریخچه‌ها، سفارش، تیکت/پیوست تیکت، پاسخ/وضعیت، پیام و درخواست اصلاح اطلاعات. فیش، پیوست سفارش دستی و عملیات مالی برای support مجاز نیستند.

مجوز در بازکردن فرم، هر state/callback و درست پیش از handler از DB دوباره خوانده می‌شود. دکمه ذخیره‌شده یا username تنها مجوز نیست. دکمه‌های اعلان تاریخی `adm:payok/payno/complete` برای سازگاری رفتار قبلی دارند و الزاماً فرم تأیید تازه باز نمی‌کنند. payload ذخیره‌شده outbox به‌خاطر این تغییر UI بازنویسی نشده است.

## قرارداد توسعه و بازیابی

- `app/admin_forms.py`: ۸۳ action متناظر با تمام DOCUMENTED_COMMANDS، فیلدها، شاخه‌های شرطی و ساخت آرگومان.
- `app/admin_ui.py`: نقش زنده، انتخابگرهای SQL فقط خواندنی، جست‌وجو، state پایدار و تأیید.
- `app/admin.py`: handler مشترک قدیمی، اعتبارسنجی و فراخوانی دامنه؛ UI منطق مالی یا SQL mutation موازی ندارد.
- `user_states.state=admin:ui`: action، actor، chat، nonce تصادفی، revision، step، values، labels، options، آخرین input و وضعیت editing/confirm/executing/done. مقادیر داخل callback فقط اشاره‌گر کوتاه هستند. secret پس از پایان موفق از state پاک می‌شود.
- هر callback مرحله‌ای token و revision دارد؛ اقدام دکمهٔ قدیمی هرگز اجرا نمی‌شود و فقط UI معتبر بازیابی می‌شود. actor دیگر یا نقش لغوشده رد می‌شود. هر بازنماییِ انتخابگر—even replay—revision تازه و نگاشت گزینهٔ ذخیره‌شدهٔ متناظر دارد؛ تغییر ترتیب رکوردها نباید index دکمهٔ قبلی را به شخص/محصول دیگری متصل کند. گزینه جدید با DB/handler دوباره اعتبارسنجی می‌شود. نسخه پیش‌نمایش متن اصلی را تغییر نمی‌دهد.
- `prompt_message_id` اختیاری، فقط پیام آخر UI در همان private chat را شناسایی می‌کند. revision/گزینه‌ها پیش از ارسال و ID پیام پس از ارسال ذخیره می‌شوند؛ سپس markup پیام قبلی با edit پاک می‌شود. خطای edit صرفاً best effort است؛ guard امنیتی به آن وابسته نیست. پیام، DB دامنه و outbox ذخیره‌شده حذف یا بازنویسی نمی‌شوند. state نسخهٔ قبلی بدون این فیلد نیز پشتیبانی می‌شود.
- `last_input` از update ID ساخته می‌شود؛ replay بعد از commit پاسخ مرحله، مرحله را دوباره جلو نمی‌برد. crash پس از آخرین فیلد نیز به confirm یا همان خواندن ادامه می‌دهد.
- پیش از handler، execution_input و executing ثبت می‌شوند. همان update موقتاً ناموفق با NACK/offset ثابت ادامه می‌یابد. برای wallet، ticket و noticeهایی که message ID مصرف می‌کنند، ID عملیاتی `ui-TOKEN` ثابت و مستقل از پیام صفحه‌کلید است.
- effect یکتای journal مدیریت برای handler/toggle محفوظ می‌ماند؛ UI effect دیگری در آن نمی‌نویسد. اثر مالی idempotent و collision-safe فعلی تغییر نکرده است.
- پاسخ مدیریتی بافر می‌شود تا done ثبت شود. اعلان‌های حیاتی در outbox دامنه می‌مانند. بافر UI پایدار نیست و exactly-once ارسال شبکه تضمین نمی‌شود؛ پس از crash یا خطای Telegram نتیجه را از فهرست بررسی کنید، نه با اجرای کور دوباره عملیات.
- جداکننده `|` در متن آزاد syntax نیست. `_command_parts` فقط در context داخلی UI آرایه اصلی را می‌دهد؛ مسیر فرمان همچنان parser قبلی را دارد. متن HTML همان validator فعلی را طی می‌کند.
- schema همان ۱۱ است؛ rollout/rollback در [deployment.md](deployment.md). توسعه‌دهنده باید [development.md](development.md)، [SECURITY.md](SECURITY.md) و تست‌های UI و دامنه را با هم بخواند.

## پذیرش و آزمون

نتیجه اجرای نهایی محلی این تغییر در 2026-09-05: مجموع ۳۲۳ تست، ۳۲۱ موفق و ۲ skip وابسته به POSIX روی Windows؛ صفر failure/error. ۲۶ تست رابط دکمه‌ای به مجموعه قبلی افزوده شده‌اند. compileall، Ruff، یکپارچگی مستندات و secret/hygiene scan پاس شدند. هر دو ویدیوی بازتولیدشده decode کامل و پخش واقعی Chromium را پاس کردند؛ نمونه فریم‌ها و رندر نمودار تازه نیز بازبینی شدند. نتیجه Linux و build تصویر Docker در CI همان commit ثبت می‌شود.

[tests/test_admin_buttons.py](../tests/test_admin_buttons.py) پوشش همه actionها و فرم‌ها، عدم تغییر منوی مشتری، مجوز و revoke، جست‌وجو/صفحه، داده pipe، عدم echo، پرداخت/کیف پول/ticket، تخفیف و combined، preview پیام گروهی، replay و crash boundary را اجرا می‌کند. mock مسیر Telegram هیچ تراکنش واقعی بانکی یا پیام واقعی به مشتری ایجاد نمی‌کند. این تست‌ها screenshot از نسخه وب کاربر نیستند و ادعای نبود همه باگ‌های ممکن ندارند. مجموعه تست قبلی دامنه نیز باید کاملاً سبز بماند.

نمودار state و activity جدید در [DIAGRAMS.md](DIAGRAMS.md) و [16-admin-button-form.mmd](diagrams/16-admin-button-form.mmd) آمده است.

ممیزی تکمیلی گزارش «این دکمه قدیمی است» در [BUTTON_UI_AUDIT.md](BUTTON_UI_AUDIT.md) ثبت شده است. تست‌های navigation اکنون callback را از keyboard واقعاً ارسال‌شده به transport آزمایشی می‌خوانند؛ ساخت callback از revision دیتابیس جای آزمون UI را نمی‌گیرد. [test_admin_ui_navigation.py](../tests/test_admin_ui_navigation.py) شامل ۲۲ تست جدید و پیمایش تمام عملیات، همه ۲۳ شاخهٔ ویرایش محصول و ۱۱ شاخهٔ گزارش/فیلتر کاربر است.
