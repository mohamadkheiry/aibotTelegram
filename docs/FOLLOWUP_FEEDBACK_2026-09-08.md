# ادامه اصلاح گزارش‌های کارفرما — ۲۰۲۶-۰۹-۰۸

این دور پنج گزارش متنی تازه و دسترسی زمینه‌دار پاداش محصول (VF-01) را پوشش می‌دهد. متن و صوت خصوصی، شناسه پیام‌ها و داده واقعی در مخزن نگهداری نمی‌شوند. این شش **گروه اصلاح/بهبود** با شش باگ مستقل یا تکمیل تمام نیازمندی‌های مالی یکسان نیستند. نتیجه آزمون و انتشار در بخش تحویل ثبت می‌شود.

## قرارداد توسعه و بازیابی

- `Database._allocate_order_number` در همان write transaction ایجاد سفارش، high-water mark را در setting `order_number_sequence` نگه می‌دارد؛ absent یعنی 999. بیشینه شماره عددی واردشده نیز رعایت می‌شود. retry همان idempotency key شماره مصرف نمی‌کند و rollback تراکنش شمارنده را نیز برمی‌گرداند. setting را دستی reset نکنید.
- `get_order(int)` برای ID داخلی، `get_order(str)` و `get_order_by_number` برای شماره عمومی دقیق‌اند. callback مشتری همچنان ID داخلیِ مالکیت‌سنجی‌شده دارد. در فرمان اختیاری `/user_orders CHAT_ID order:1000`، پیشوند `order:` ابهام شماره با صفحه را رفع می‌کند؛ عدد تنها همچنان صفحه است. در جست‌وجوی کاربر نیز `order:1000` را با chat ID عددی اشتباه نگیرید.
- `customer_info_json` بدون تغییر schema، `messages[]`، `collection_id` و `collecting` می‌گیرد. هر پیام text/file_id/file_kind/telegram_message_id دارد؛ فیلد text سطح بالا تجمیع متن‌ها و file_id سطح بالا نخستین فایل معتبر برای سازگاری خواندن است. `order_information.py` فقط projection است؛ mutation و مالکیت در DB می‌ماند.
- `begin_manual_information` ادامه مجموعه باز را برمی‌گرداند؛ `append_manual_information` هیچ قسمت قبلی را حذف نمی‌کند؛ `finish_manual_information` پایان، processing، outbox ACK و پاک‌کردن state همان مجموعه را اتمیک می‌کند. ACK گمشده و alert مدیر از outbox/reconciliation بازیابی می‌شوند. دکمه پایان مجموعه قدیمی نمی‌تواند مجموعه تازه را ببندد. تکمیل در collecting رد است، حتی اگر status از دور قبل processing باشد.
- اصلاح مشتری append می‌شود و متن‌های قبلی برای بررسی باقی می‌مانند؛ آخرین متن را به‌عنوان جایگزین مخفیِ اطلاعات قبلی ذخیره نکنید. state تک‌پیامی باز از نسخه قبل فقط برای همان ورودی مسیر سازگار قدیمی دارد؛ شروع تازه مسیر چندپیامی است.
- body/markup اعلان مدیریتی manual و پیام تکمیل قبلاً commit‌شده پس از upgrade بازنویسی نمی‌شوند. این استثنا scoped به همان کلید پایدار و گیرنده است؛ idempotency عمومی ضعیف نمی‌شود.
- registry هنوز ۴۲ نوع صفحه دارد؛ `input_order_info` دو slot finish/cancel دارد. چیدمان قدیمی بدون حذف تنظیم مدیر، finish را قبل cancel می‌گیرد. رنگ colored و آیکون‌های manifest در مرز transport حفظ‌اند.
- قواعد پاداش این نسخه همچنان **مبلغ ثابت به معرف** هستند؛ این UI پرداخت جدید خودکار یا جایگزینی قواعد نمی‌سازد. مقصد فعال/غیرفعال در تأیید freeze و journal موجود دوباره‌کاری را مهار می‌کند.

## تصمیم‌های باز و خارج دامنه

[VF-02 و VF-03](VOICE_FEEDBACK_2026-09-08.md) هنوز بازند: درصد و سقف هر محصول، مبنای مبلغ/گردکردن، زمان واریز پس از پرداخت یا تحویل، و هم‌زمانی با قواعد ثابت/عمومی به تصمیم مالک نیاز دارند. سؤال‌ها از کاربر پرسیده شده‌اند؛ انتخاب پیش‌فرض فرم سؤال پاسخ محسوب نمی‌شود. کم‌واریزی و پل بانکی/ارزی نیز تأیید واقعی نشده‌اند. cashback شخص خریدار صریحاً فاز دوم است.

هیچ پاداش، روش پرداخت، نقش یا داده تجاری production برای تست تغییر داده نمی‌شود. push عمومی تازه به GitHub تا روشن‌شدن محرمانگی ممنوع است؛ commit و bundle خصوصی مسیر تحویل جاری‌اند. پیام پایان کامل به کارفرما نباید موارد باز را پنهان کند.

## آزمون و تحویل

`tests/test_followup_feedback.py` با SQLite واقعی موقت و Telegram شبیه‌سازی‌شده، شماره‌گذاری هم‌زمان/replay/rollback/import، چندپیام و چندفایل، restart، مالکیت، پایان خالی/قدیمی، outbox قبلی، جست‌وجوی واقعی، سربرگ غنی، پاداش زمینه‌دار/تأیید/بیش از ۱۰۰ قانون و چیدمان قدیمی را پوشش می‌دهد. سفر پرداخت تا اصلاح اطلاعات و تکمیل در `test_spec_end_to_end.py` نیز به پایان صریح متصل شده است.

نسخه نهایی با **۵۴۶ تست Linux در ۶۶٫۱۷۷ ثانیه، بدون failure/error/skip** پذیرفته و commit `7c7287604584bce169248039c49191ba2261a549` ساعت ۱۸:۳۴:۰۹ تهران روی میزبان مصوب و ربات جدید منتشر شد. ۲۷ تست نسبت به suite قبلی افزوده شده‌اند. [SHA، بکاپ/بازیابی و شواهد سلامت](CURRENT_DEPLOYMENT.md). شش گروه این دور با ۲۵ گروه قبلی جمعاً ۳۱ گروه‌اند؛ VF-02/VF-03 مالی باز و ادعای «همه چیز تمام شد» نادرست است.

Rollback به نسخه تک‌پیامی بدون بررسی مجاز نیست: آن نسخه `messages/collecting` را نمی‌شناسد و ممکن است با ورودی بعدی اطلاعات چندقسمتی را جایگزین کند. DB جاری و JSON چندپیامی باید حفظ شوند؛ برای rollback، اصلاح سازگاری خواندن/append را نگه دارید یا ابتدا با مالک همه مجموعه‌های باز را تعیین تکلیف کنید. DB قدیمی روی سفارش تازه restore نشود.
