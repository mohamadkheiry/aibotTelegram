# چیدمان دکمه‌های کاربران

درخواست جدید مالک محصول، ثابت‌بودن **چیدمان پیش‌فرض** سند را به «پیش‌فرض قابل تغییر توسط مدیر» تبدیل می‌کند. رنگ، عنوان، مقصد، مجوز و شرط نمایش دکمه‌ها تغییر نمی‌کند. هر جا اسناد قبلی از منوی ثابت نام می‌برند، منظور از این نسخه به بعد چیدمان اولیه و قابل بازنشانی است. پنل اصلی مدیریت همچنان ۹ بخش دارد.

## مسیر و روش کار مدیر

`پنل مدیریت ← مدیریت کلی ربات ← چیدمان دکمه‌های کاربران`

۱. گروه و صفحه را انتخاب کنید. برای دسته/محصول/FAQ می‌توانید الگوی مشترک یا همان مورد مشخص را انتخاب کنید؛ فهرست‌ها جست‌وجو و صفحه‌بندی دارند.
۲. پیش‌نمایش امن را ببینید. لمس دکمهٔ «خرید»، لینک یا پرداخت در پیش‌نمایش فقط آن دکمه را انتخاب می‌کند و هیچ خرید، ارسال اطلاعات یا پرداختی اجرا نمی‌شود.
۳. با «تک‌ستونه / دوستونه / سه‌ستونه» چیدمان سریع بسازید. دکمهٔ انتخاب‌شده را به ابتدا/انتها یا ردیف مستقل ببرید؛ با «کنار ردیف قبلی/بعدی» ردیف مشترک بسازید و با چپ/راست ترتیب داخل آن را عوض کنید. «ردیف بالاتر/پایین‌تر» کل همان ردیف را جابه‌جا می‌کند.
۴. فهرست متغیر بلوک مستقل دارد؛ ستون‌هایش جداگانه قابل تنظیم‌اند. برای دسته‌ها، محصولات، سؤال‌ها و کانال‌ها، «مرتب‌کردن تک‌تک گزینه‌های فهرست» را بزنید: یک مورد را انتخاب و بالا/پایین، ابتدا/انتها یا «انتخاب جایگاه دلخواه» را استفاده کنید. مرتب‌سازی روی **کل فهرست و پیش از صفحه‌بندی کاربر** اعمال می‌شود، نه فقط صفحهٔ اول.
۵. «پیش‌نمایش نهایی و انتشار ← تأیید انتشار» را بزنید. تا تأیید نهایی، تغییر صرفاً پیش‌نویس همان مدیر است. «لغو تغییرات و بازگشت» اثری روی کاربران ندارد. «بازخوانی نسخه ذخیره‌شده» پیش‌نویس را با آخرین نسخه جایگزین می‌کند.
۶. پس از انتشار، «بازگشت به چیدمان قبلی» آخرین نسخه را با تأیید برمی‌گرداند؛ حداکثر ۱۰ تغییر ذخیره‌شده قابل واگرد است. «بازنشانی به چیدمان اولیه» جداست و چیدمان اولیهٔ سند را برمی‌گرداند؛ خود بازنشانی هم قابل واگرد است.

تغییر از **نمایش بعدی همان بخش** اعمال می‌شود؛ پیام‌های قدیمیِ ارسال‌شده به همه کاربران ویرایش جمعی نمی‌شوند. انتخاب‌های قدیمی همچنان callback اصلی خود را دارند و کنترل مالکیت/وضعیت فعلی سرور را طی می‌کنند. مدیر دوم نمی‌تواند روی پیش‌نویس قدیمی، تغییر تازهٔ مدیر دیگر را بازنویسی کند؛ ابتدا باید نسخه را بازخوانی کند.

صفحهٔ تک‌دکمه‌ای نیز در فهرست وجود دارد، ولی جابه‌جایی تنها دکمه طبعاً تغییر قابل مشاهده‌ای نمی‌دهد. کلاینت Telegram ظاهر نهایی و عرض دکمه‌ها را تعیین می‌کند؛ در این نسخه برای خوانایی فارسی یک تا سه دکمه در هر ردیف قابل انتخاب است. دکمه‌ها حذف، مخفی، تغییرنام یا به بخش دیگری منتقل نمی‌شوند؛ درخواست حاضر تنظیم موقعیت در **همان بخش** است.

## معماری و قرارداد توسعه

- `app/customer_layouts.py`: registry واحد `SECTIONS`، schema تنظیم، تطبیق slot، reflow بدون حذف و `LayoutEngine`/`LayoutTelegram`.
- `app/admin_layouts.py`: ویرایشگر با state پایدار `admin:layouts`؛ actor/chat، nonce/revision، گزینه‌های صادرشده، draft، نسخه مبنا و phase. فرم‌های سازگار قبلی تغییر نکرده‌اند و فرمان جدید اجباری نیست.
- `app/bot.py` و `app/keyboards.py`: همه markupهای کاربر section صریح دارند. پنج محل inline بدون section در bot، فقط اعلان/ورودی مدیریت‌اند. `remove_keyboard` و پاک‌سازی markup کنترل نمایشی حذف کیبوردند، نه یک صفحهٔ دکمه‌ای.
- ترتیب فهرست‌های عمومی قبل از slice در `show_store/show_category/show_faq_categories/show_faqs/_show_join_required` اعمال می‌شود. چیدمان ردیف‌ها روی کپی markup هنگام send/edit/copy/document/photo اعمال می‌شود. هیچ poller یا client شبکهٔ دوم ساخته نمی‌شود.
- `_customer_layout` فقط شناسه صفحه است؛ `_layout_slot` و `_layout_item` فقط presentation metadata داخلی‌اند و در مرز Telegram حذف می‌شوند. نام عمومی مساوی «بازگشت» یا «صفحه قبل» به navigation بازتفسیر نمی‌شود؛ slot و شناسهٔ اصلی تعیین‌کننده‌اند.
- دکمه‌های شرطی از ورودی موجود مرتب می‌شوند: engine هیچ callback، URL، copy payload، contact request، style یا icon را از تنظیم مدیر تولید نمی‌کند. گزینه ناشناختهٔ آینده حذف نمی‌شود و انتهای کیبورد باقی می‌ماند؛ تست پوشش مانع اضافه‌شدن بی‌صدای صفحهٔ ثبت‌نشده است.
- آیکون اختیاری از manifest عملیاتی مستقل [BUTTON_ICONS.md](BUTTON_ICONS.md) در کپی خروجی اضافه می‌شود، نه از draft چیدمان مدیر. آیکون صریح حفظ می‌شود؛ `theme` نیز صرفاً style را در مرز HTTP کنار می‌گذارد. این دو لایه callback، contact، داده canonical و نسخهٔ چیدمان را تغییر نمی‌دهند.

## داده، نسخه‌بندی و بازیابی

Schema همچنان ۱۱ است. کلید `settings.customer_layout:SECTION` سندی شامل `current`، `version`، `history` حداکثر ۱۰ نسخه، `updated_by` و `updated_at` نگه می‌دارد. current شامل فقط `rows` (slotها)، `columns` (۱..۳)، `item_order` (شناسه‌های کاتالوگ عمومی) و `reverse` است. کلید موردی مثل `product:12` تا پیش از ذخیره از `product` ارث می‌برد؛ override مستقل است و reset، پیش‌فرض سند را صریح ذخیره می‌کند.

تاریخچه، چیدمان مؤثرِ قبلی را ذخیره می‌کند؛ حتی اگر آن چیدمان از الگوی مشترک ارث رسیده باشد، تغییر بعدی الگو معنای واگرد را عوض نمی‌کند. بدون تنظیم سفارشی یا پس از بازنشانی، ترتیب و ردیف‌های اصلی builder عیناً حفظ می‌شوند؛ از جمله دکمه‌های تکرارشوندهٔ پرداخت‌های قدیمی.

`Database.save_customer_layout` مجوز زنده owner/admin را داخل transaction دوباره بررسی می‌کند و نسخهٔ بخش و نسخهٔ الگوی والد را مقایسه می‌کند. تعارض نسخه خطای terminal قابل بازخوانی است؛ اثر دیگران بازنویسی نمی‌شود. ذخیره تنظیم و ثبت نتیجه در همان effect موجود `processed_admin_updates` اتمیک‌اند. اجرای مجدد همان update همان نتیجه را برمی‌گرداند؛ request متفاوت collision است. draft پیش از اجرا به `executing` می‌رود و replay پس از crash اثر را دوباره نمی‌سازد. پشتیبان، کاربر عادی، private chat ناسازگار، نقش لغوشده و callback قدیمی نمی‌توانند تغییر را منتشر کنند.

Outbox نسخهٔ canonical را نگه می‌دارد، نه شکل شخصی‌سازی‌شدهٔ ارسال. idempotencyِ پیام علاوه بر recipient/body و تمام ویژگی‌های واقعی markup، فقط metadata داخلی نمایش را هنگام مقایسه legacy نادیده می‌گیرد؛ تغییر مقصد، مقدار کپی، عنوان یا ردیف واقعی همچنان conflict است. هیچ پیام ذخیره‌شده‌ای برای ظاهر بازنویسی نمی‌شود. پیام‌های قدیمی بدون tag با شکل قدیمی قابل retry هستند.

## rollout، rollback و آزمون

ابتدا backup تأییدشده؛ سپس توقف تنها poller، استقرار commit سبز و راه‌اندازی یک poller. migration و تغییر داده کاتالوگ/مالی لازم نیست. تست زنده فقط بازکردن ویرایشگر و لغو پیش‌نویس باشد؛ تست انتشار/بازگردانی روی SQLite و Telegram ساختگی اجرا می‌شود.

برای بازگردانی ظاهر، دکمهٔ بازنشانی هر بخش یا تنظیم عملیاتی `customer_layouts_enabled=false` از API `Database.set_setting` قابل استفاده است. کلید پیش‌فرض true است؛ false همه ترتیب‌های سفارشی و reflow را بدون حذف تنظیمات غیرفعال می‌کند و metadata همچنان پاک می‌شود. برای فعال‌کردن دوباره true کنید. این تنظیم اپراتوری جای دکمهٔ واگرد مدیر نیست. برای rollback کد به نسخه‌ای پیش از معرفی metadata، decoder پاک‌سازی را حفظ/backport کنید؛ صرفاً بازیابی backup قدیمی روی دیتابیس دارای سفارش تازه مجاز نیست.

شواهد دائمی: `tests/test_customer_layouts.py` (تمام templateها، subset شرطی، برابری payload، inheritance، sort پیش از صفحه‌بندی، fallback، transport و AST coverage) و `tests/test_admin_layouts.py` (دکمهٔ واقعی صادرشده، لغو/انتشار/واگرد، restart، stale، تعارض، revoke و crash). suite اصلی خرید، کیف پول، پرداخت و outbox نیز باید سبز بماند. نتیجهٔ دقیق اجرای هر انتشار در CI همان commit معیار پذیرش است؛ این تست‌ها ادعای نبود مطلق هر باگ ممکن نیستند.
