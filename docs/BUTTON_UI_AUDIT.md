# ممیزی جامع رابط دکمه‌ای — 2026-09-05

یادداشت نسخه بعد: بخش‌های اولیهٔ این گزارش سابقهٔ اصلاح UI-A01/UI-A02 و نتایج همان انتشارند؛ اصلاح‌های تکمیلی در ابتدای سند آمده‌اند. ساختار ۱۳گروهی قبلی اکنون با ۹ بخش سند و درخت دسته/محصول جایگزین شده؛ گزارش جاری در [ADMIN_HIERARCHY.md](ADMIN_HIERARCHY.md) است. تست رسیدن به actionها، زیرگروه‌ها و مرور موجودیت‌محور را جداگانه پوشش می‌دهد و پوشش ۸۳ handler سازگار حفظ شده است.

## زمینهٔ روش پرداخت — UI-A05/UI-A06

کاربر با تصویر مرحلهٔ «وضعیت جدید» گزارش داد مشخص نیست کدام روش پرداخت انتخاب شده و اکنون فعال است یا غیرفعال. دو تست بازتولید روی پایه `a1c11ea` این دو کمبود را تأیید کردند؛ آزمون وضعیت هر سه روش در هر دو حالت نیز ناموفق بود.

- **UI-A05:** نام فارسی روش انتخاب‌شده در مرحله وضعیت، تأیید، نتیجه و بازیابی نمایش داده می‌شود؛ با برگشت و انتخاب مجدد، نام قبلی باقی نمی‌ماند.
- **UI-A06:** وضعیت فعلی از flag همان روش در DB تازه خوانده می‌شود و از وضعیت جدیدِ هنوز تأییدنشده جداست. نقص پیکربندی کارت/رمزارز به‌صورت هشدار بدون افشای مقادیر محرمانه نمایش داده می‌شود.

`AdminButtonUI.payment_context` فقط روش allowlistشده را می‌خواند؛ label ذخیره‌شده یا نام دلخواه setting مبنا نیست. schema، handler پرداخت، پارامتر هدف، تأیید و journal تغییر نکرده‌اند. ۱۲ تست اختصاصی در [test_admin_payment_context.py](../tests/test_admin_payment_context.py) از keyboard/message ID واقعیِ FakeTelegram استفاده می‌کنند: هویت، هر سه روش/هر دو وضعیت، فعلی در برابر جدید، نتیجه، back/cancel، stale و تغییر هم‌زمان، restart، state قدیمی، تنظیمات ناقص، role/private chat، crash/replay و داده نامعتبر. نتیجه کل suite در CI همان commit ثبت می‌شود. هیچ روش پرداخت production برای آزمون فعال/غیرفعال نمی‌شود و این آزمون‌ها تست بصری کلاینت واقعی تلگرام نیستند.

اجرای هدفمند محلی: هر ۴۹ تست زمینه پرداخت، فرم‌های مدیریت و دکمه وضعیت ربات در ۱۵۲٫۲۸۷ ثانیه موفق شدند؛ ۱۱ تست مستقل invariantهای انتشار/پرداخت نیز موفق بودند. lint و compile پاس شدند. مجموعه کامل در Linux CI همان commit اجرا می‌شود؛ آمار بخش‌های بعدی مربوط به انتشارهای قبلی است.

## اصلاح تکمیلی دکمه‌های وضعیت — UI-A03/UI-A04

گزارش بعدی کاربر: دکمهٔ فعال‌کردن ربات و حالت تعمیرات، وضعیت معکوس را نشان نمی‌دادند. روی پایه `67e162e` دو تست رگرسیون با keyboard واقعاً ارسال‌شده، برای حالت فعال و غیرفعال هر دو شکست خوردند: منو همیشه «فعال‌کردن ربات» و «حالت تعمیرات» بود. handler خاموش‌کردن موجود بود؛ اشکال در label/انتخاب عمل متناسب با وضعیت و نبود دکمهٔ معکوس پس از اجرا بود.

دو مورد گزارش‌شده در این اصلاح رفع شدند:

- **UI-A03:** دکمهٔ ربات از `bot_enabled` خوانده می‌شود؛ فعال → غیرفعال‌کردن، غیرفعال → فعال‌کردن.
- **UI-A04:** دکمهٔ تعمیرات و پیام نتیجه با همان وضعیت هماهنگ‌اند؛ تعمیرات فعال → غیرفعال‌کردن تعمیرات و برعکس.

`AdminButtonUI.bot_status` تنها متن و keyboard می‌سازد. هدف صریح callback به handler موجود می‌رود؛ toggle مبتنی بر وضعیت لحظهٔ اجرا، SQL mutation جدید، schema جدید یا flag دوم تعمیرات اضافه نشده است. تأیید، وضعیت فعلی/مقصد و محفوظ‌بودن دسترسی مدیران را نشان می‌دهد. بعد از موفقیت یا بازیابی نتیجه، عمل معکوس قابل انتخاب است. [قرارداد کاربری](BUTTON_UI.md).

۱۱ تست اختصاصی در [test_admin_bot_status.py](../tests/test_admin_bot_status.py) از keyboard و message ID خروجی استفاده می‌کنند: هر دو وضعیت، رفت‌وبرگشت هر دو دکمه، لغو، هدف ثابت دکمهٔ قدیمی، دوبار تأیید، تغییر بعدی و replay قبلی، restart و بازگرداندن دسترسی مشتری، private chat و revoke، crash پیش/پس از commit و failure پاک‌سازی markup. تست‌ها DB موقت و FakeTelegram دارند؛ خاموش/روشن‌کردن ربات واقعی بخشی از آزمون نیست. نتیجه suite کامل در CI همان commit ثبت می‌شود؛ اعداد بخش‌های زیر سابقهٔ release اولیه‌اند.

اجرای محلی این اصلاح: ۵۹ تست هدفمند UI موفق و suite کامل ۳۹۰ تست در ۴۹۲٫۵۰۷ ثانیه بدون failure/error بود؛ دو تست مخصوص POSIX روی Windows skip شدند. نمودار فرم و اسلاید تنظیمات به‌روز شدند؛ ویدیوها کنترل بیرون‌زدگی، decode کامل و پخش مرورگری را پاس کردند. آزمون تصویری اسلاید آموزشی جای آزمون کلاینت واقعی تلگرام را نمی‌گیرد.

## گزارش و علت اولیه

گزارش کاربر: لمس «همه / بدون محدودیت» در فهرست پرسش‌ها پیام «این دکمه قدیمی است؛ از آخرین پیام فرم استفاده کنید» می‌دهد.

روی نسخهٔ پایه `1902b5b` و دیتابیس کاملاً آزمایشی، نخستین کلیک نتیجهٔ خالی FAQ را به‌درستی نمایش می‌داد، ولی keyboard مصرف‌شده روی پیام قبلی باقی می‌ماند. کلیک بعدی به revision پایان‌یافته می‌رسید و فقط هشدار می‌داد. بررسی فقط‌خواندنی metadata محیط اجرا نیز state پایان‌یافتهٔ `faqs` را نشان داد؛ محتوای خصوصی کاربران یا credentialها در این گزارش ثبت نشده است.

## روش آزمون

- سه تست بازتولید، با بارگذاری کد پایه در حافظهٔ process مستقل، هر سه شکست خوردند؛ فایل کد یا دیتابیس محیط اجرا برای این بررسی تغییر نکرد.
- ۲۲ تست جدید در `tests/test_admin_ui_navigation.py`؛ انتخاب بر اساس label یا callback موجود در keyboard خروجی، همراه با message ID و markup همان پیام.
- helper کلیک در ۲۶ تست قبلی نیز به keyboard خروجی متصل شد؛ ساخت عمدی payload در تست‌های جعل/replay همچنان مجاز است.
- ورود از ۱۳ بخش به تمام ۸۳ عملیات؛ routing تمام فرم‌ها به handler ثبت‌شده در تست قبلی، بدون تایپ فرمان.
- اجرای واقعی تمام ۲۳ شاخهٔ ویرایش محصول در دیتابیس آزمایشی، حفظ متن pipe و مقادیر ساختاری؛ تمام چهار نوع گزارش و هفت فیلتر کاربر از دکمه‌ها.
- FAQ خالی و غیرخالی، جست‌وجو، ۲۴ رکورد/صفحه‌بندی، تمام‌کردن چندانتخابی، اصلاح مرحله، لغو، منوی اصلی و `/start`.
- نقش لغوشده، فرم دیگر، ورودی قدیمی، کلیک دوبارهٔ تأیید مالی، شکست ارسال نتیجه، شکست edit و crash پس از ذخیرهٔ شناسهٔ پیام تازه.
- اجرای تمام suite موجود برای سفارش، پرداخت/کیف پول، انبار/FIFO، referral، تیکت، migration، journal، outbox، امنیت، منو و مستندات؛ به‌علاوه Ruff و compileall. نتیجهٔ نهایی هر commit در CI همان commit ثبت می‌شود.

## مرز ادعا

نتیجهٔ نهایی محلی: ۳۴۵ تست در ۳۲۱٫۲۴۶ ثانیه، ۳۴۳ موفق و دو skip وابسته به POSIX روی Windows؛ صفر failure/error. Ruff، compileall و هشت تست یکپارچگی مستندات/مخزن نیز پاس شدند. نمودار ۱۶ از source Mermaid به SVG بازتولید و PNG آن از نظر خوانایی و قطع‌نشدن متن بازبینی شد. اجرای مستقل Linux، build Docker و smoke migration کانتینر در CI همین release ثبت می‌شود.

Telegram در تست‌ها `FakeTelegram` است و داده‌ها ساختگی‌اند. هیچ پرداخت واقعی، اعتباردهی واقعی، پیام گروهی یا ارسال آزمایشی به مشتری انجام نشده است. این آزمون‌ها مسیر backend و payload واقعی تولیدشدهٔ keyboard را می‌سنجند، نه screenshot یا کلیک در کلاینت وب واقعی کاربر. پیام completion به مالک پس از rollout عملیاتی از این آزمون‌ها جداست. موفقیت مجموعهٔ تست به‌معنای اثبات نبود همهٔ باگ‌های ممکن نیست.

## استقرار و rollback

schema همچنان ۱۱ است؛ تنظیم، token، مجوز ادمین‌ها و ترتیب/رنگ منوی مشتری تغییر نمی‌کند. state موجود بدون `prompt_message_id` معتبر است و پس از کلیکِ دارای token منطبق، همان پیام برای cleanup شناخته می‌شود. دقیقاً یک poller `getUpdates` باید اجرا شود؛ تست هیچ poller دیگری راه نمی‌اندازد.

پیش از restart، بکاپ آنلاین معتبر و integrity/FK check لازم است. سپس فقط process مربوط به همین env متوقف و release آزموده‌شده جایگزین می‌شود. rollback کد به نسخهٔ قبل نیاز به downgrade دیتابیس ندارد، چون field تازه داخل JSON اختیاری است؛ با این حال رفتار stale قدیمی بازمی‌گردد. پیام‌های قدیمی ممکن است به‌علت محدودیت Telegram یا قطع شبکه قابل edit نباشند؛ recovery و guardها باید مستقل از cleanup درست بمانند.
