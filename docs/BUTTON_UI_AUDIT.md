## روش آزمون

- سه تست بازتولید، با بارگذاری کد پایه در حافظهٔ process مستقل، هر سه شکست خوردند؛ فایل کد یا دیتابیس محیط اجرا برای این بررسی تغییر نکرد.
- ۲۲ تست جدید در `tests/test_admin_ui_navigation.py`؛ انتخاب بر اساس label یا callback موجود در keyboard خروجی، همراه با message ID و markup همان پیام.
- helper کلیک در ۲۶ تست قبلی نیز به keyboard خروجی متصل شد؛ ساخت عمدی payload در تست‌های جعل/replay همچنان مجاز است.
- ورود از ۱۳ بخش به تمام ۸۳ عملیات؛ routing تمام فرم‌ها به handler ثبت‌شده در تست قبلی، بدون تایپ فرمان.
- اجرای واقعی تمام ۲۳ شاخهٔ ویرایش محصول در دیتابیس آزمایشی، حفظ متن pipe و مقادیر ساختاری؛ تمام چهار نوع گزارش و هفت فیلتر کاربر از دکمه‌ها.
- FAQ خالی و غیرخالی، جست‌وجو، ۲۴ رکورد/صفحه‌بندی، تمام‌کردن چندانتخابی، اصلاح مرحله، لغو، منوی اصلی و `/start`.
- نقش لغوشده، فرم دیگر، ورودی قدیمی، کلیک دوبارهٔ تأیید مالی، شکست ارسال نتیجه، شکست edit و crash پس از ذخیرهٔ شناسهٔ پیام تازه.
- اجرای تمام suite موجود برای سفارش، پرداخت/کیف پول، انبار/FIFO، referral، تیکت، migration، journal، outbox، امنیت، منو و مستندات؛ به‌علاوه Ruff و compileall. نتیجهٔ نهایی هر commit در CI همان commit ثبت می‌شود.

## مرز ادعا

نتیجهٔ نهایی محلی: ۳۴۵ تست در ۳۲۱٫۲۴۶ ثانیه، ۳۴۳ موفق و دو skip وابسته به POSIX روی Windows؛ صفر failure/error. Ruff، compileall و هشت تست یکپارچگی مستندات/مخزن نیز پاس شدند. نمودار ۱۶ از source Mermaid به SVG بازتولید و PNG آن از نظر خوانایی و قطع‌نشدن متن بازبینی شد. اجرای مستقل Linux، build Docker و smoke migration کانتینر در CI همین release ثبت می‌شود.

Telegram در تست‌ها `FakeTelegram` است و داده‌ها ساختگی‌اند. هیچ پرداخت واقعی، اعتباردهی واقعی، پیام گروهی یا ارسال آزمایشی به مشتری انجام نشده است. این آزمون‌ها مسیر backend و payload واقعی تولیدشدهٔ keyboard را می‌سنجند، نه screenshot یا کلیک در کلاینت وب واقعی کاربر. پیام completion به مالک پس از rollout عملیاتی از این آزمون‌ها جداست. موفقیت مجموعهٔ تست به‌معنای اثبات نبود همهٔ باگ‌های ممکن نیست.

## استقرار و rollback

schema همچنان ۱۱ است؛ تنظیم، token، مجوز ادمین‌ها و ترتیب/رنگ منوی مشتری تغییر نمی‌کند. state موجود بدون `prompt_message_id` معتبر است و پس از کلیکِ دارای token منطبق، همان پیام برای cleanup شناخته می‌شود. دقیقاً یک poller `getUpdates` باید اجرا شود؛ تست هیچ poller دیگری راه نمی‌اندازد.

پیش از restart، بکاپ آنلاین معتبر و integrity/FK check لازم است. سپس فقط process مربوط به همین env متوقف و release آزموده‌شده جایگزین می‌شود. rollback کد به نسخهٔ قبل نیاز به downgrade دیتابیس ندارد، چون field تازه داخل JSON اختیاری است؛ با این حال رفتار stale قدیمی بازمی‌گردد. پیام‌های قدیمی ممکن است به‌علت محدودیت Telegram یا قطع شبکه قابل edit نباشند؛ recovery و guardها باید مستقل از cleanup درست بمانند.
