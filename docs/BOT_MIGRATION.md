# انتقال هویت ربات با حفظ سوابق

مالک در ۲۰۲۶-۰۹-۰۶ مقصد `@ElevenaccountsTestbot` و انتقال **همهٔ داده‌ها و سوابق فعلی** را صریحاً تأیید کرد. وضعیت اجرایی نهایی در [CURRENT_DEPLOYMENT.md](CURRENT_DEPLOYMENT.md) ثبت می‌شود؛ این runbook به‌تنهایی ادعای انتشار نیست.

## دامنهٔ دادهٔ بررسی‌شده

مبدأ در زمان آماده‌سازی ۴ کاربر، ۳ مدیر، ۲ دسته، یک تیکت با دو پیام و یک تصویر پیوست، ۱۴ اعلان ارسال‌شده و یک رکورد بکاپ دارد. محصول، موجودی، سفارش، پرداخت، دفترکل کیف پول، پاداش، کانال اجباری و broadcast ندارد. دو فرم باز و journal اجرای مدیران نیز وجود دارند؛ این‌ها سابقهٔ کسب‌وکار نیستند و به bot ID قبلی تعلق دارند.

ابزار [migrate_bot_identity.py](../tools/migrate_bot_identity.py) مخصوص همین مجموعهٔ پیش از فروش است. جدول مالی/انبار/provider/broadcast غیرخالی، اثر مدیریتی ناتمام، صف ارسال فعال، schema غیر از ۱۱ یا پیوست بدون نگاشت را **قبل از ساخت مقصد رد می‌کند**. برای دیتابیس آیندهٔ دارای فروش، این ابزار را با حذف guardها استفاده نکنید؛ مهاجرت اختصاصی و تست مالی لازم است. پذیرش «همهٔ داده‌ها» دربارهٔ داده‌های واقعی فعلی است، نه ادعای پشتیبانی عمومی از هر دیتابیس ممکن.

## چه چیزی حفظ و چه چیزی جدا می‌شود؟

| داده | رفتار |
|---|---|
| کاربران، نقش/اثبات هویت مدیران، تنظیمات و وضعیت ربات، دسته‌ها، تیکت و متن کامل مکالمه | با همان شناسه و محتوای تجاری حفظ می‌شوند. |
| تصویر تیکت | اصل فایل با SHA-256 نگه‌داری؛ برای همان فرستنده در ربات مقصد upload و file ID جدید با getFile تأیید می‌شود. هیچ داده‌ای برای فرد جدید یا مدیر نامرتبط ارسال نمی‌شود. |
| کل دیتابیس قبلی | با SQLite backup در آرشیو مستقل و با integrity/FK سالم نگه‌داری؛ فایل اصلی نیز دست‌نخورده می‌ماند. |
| فرم‌های باز، journal updateهای قبلی، offset، شناسهٔ پیام‌های ارسال‌شده | نسخهٔ اصلی کامل در آرشیو است؛ در runtime مقصد فرم/journal خالی و offset از صفر است. message ID قدیمی به‌عنوان پیام ربات جدید استفاده نمی‌شود. |
| کلیدهای idempotency ورودی‌های تاریخی | در کپی مقصد با `legacy-bot:SOURCE_ID:` namespaced می‌شوند تا update ID مشابه از ربات جدید با تیکت یا دستور قدیمی اشتباه نشود؛ مقدار اصلی در آرشیو محفوظ است. |
| کلیدهای outbox و وضعیت اعلان ارسال‌شده | بدون تغییر حفظ می‌شوند تا reconciliation اعلان قدیمی را دوباره نفرستد؛ فقط message ID مختص تلگرام قبلی از runtime حذف می‌شود. |

پس از تبدیل، همهٔ ردیف‌های همهٔ جدول‌ها با طرح تبدیل صریح مقایسه می‌شوند؛ مقایسه صرفاً شمارش نیست. منبع و آرشیو باید دقیقاً برابر باشند. وضعیت خاموش/روشن، روش پرداخت و نقش‌ها خودکار تغییر نمی‌کنند.

## ترتیب عملیات

1. مقصد و مبدأ را با `getMe` و توکن‌های خصوصی تأیید کنید. دایرکتوری داده/آرشیو/فایل‌ها و env خارج Git با ACL محدود ساخته شود.
2. فرستندهٔ پیوست باید مقصد را Start کرده باشد. ابزار انتقال پیوست فقط فایل را برای همان شخص بازبارگذاری می‌کند، پیام توضیحی بی‌صدا دارد و هیچ `getUpdates` یا mutation دیتابیس انجام نمی‌دهد.
3. journal انتقال فایل قبل از upload ثبت می‌شود. نتیجهٔ مبهم خودکار دوباره ارسال نمی‌شود؛ ID برگشتیِ ثبت‌شده بعد از شکست مرحلهٔ verification قابل تأیید مجدد بدون upload است.
4. بکاپ آنلاین مبدأ را بررسی؛ PID/فرمان/env دقیق process مبدأ را تأیید و آن را متوقف کنید. نبود poller مبدأ و ناتمام‌نبودن اثر/queue را کنترل کنید.
5. با مسیرهای تازه و متمایز migration را اجرا کنید؛ ابزار هیچ فایل مقصد یا آرشیوی را overwrite نمی‌کند. پس از هر خطا مقصد ناقص را راه‌اندازی نکنید.
6. env مقصد به DB مستقل و همان owner/grantهای حفظ‌شده اشاره کند. `--check` بدون poller اجرا و بعد فقط یک process از commit آزموده‌شده شروع شود. pending updateها حذف نشوند.
7. انتقال فایل، تاریخچهٔ تیکت و نقش‌ها، منوی جدید، offset و یک چرخه maintenance بررسی شوند. خرید/پول واقعی برای smoke لازم نیست.
8. فقط از ربات جدید به مدیران قابل دسترس اطلاع دهید. وضعیت آیکون‌ها و محدودیت روشن‌بودن لپ‌تاپ را جداگانه اعلام کنید.

```console
python tools/transfer_ticket_attachments.py --source-env SOURCE_ENV --target-env TARGET_ENV --source-db SOURCE_DB --directory PRIVATE_ASSET_DIR --source-bot-id SOURCE_ID --target-bot-id TARGET_ID
python tools/migrate_bot_identity.py --source SOURCE_DB --target NEW_DB --archive ARCHIVE_DB --source-bot-id SOURCE_ID --target-bot-id TARGET_ID --source-username SOURCE_USERNAME --target-username TARGET_USERNAME --attachment-map PRIVATE_ASSET_DIR/attachment-map.json --source-stopped
```

env و mapping شامل credential یا شناسهٔ خصوصی‌اند؛ در فرمان فقط مسیر فایل بیاید. تمام فایل‌های backing بکاپ تاریخی نیز باید در محل خصوصی قبلی محفوظ و قابل بازیابی بمانند؛ انتقال بعدی به سرور دیگر باید آن فایل‌ها و آرشیو تصویر اصلی را هم بسته‌بندی کند، نه فقط DB runtime جدید را.

## آزمون و rollback

۱۲ تست مستقل در [test_bot_identity_migration.py](../tests/test_bot_identity_migration.py) و [test_bot_attachment_transfer.py](../tests/test_bot_attachment_transfer.py) حفظ محتوا و نقش/وضعیت، namespace، عدم replay، رد overwrite، ناتمام‌بودن عملیات، داده مالی خارج دامنه، تبدیل/بازیابی فایل، خطای مبهم upload و عدم افشای URL محرمانه را می‌سنجند. suite کامل و lint نیز باید روی release موفق باشند.

Rollback پیش از دریافت دادهٔ جدید: مقصد را stop و source اصلی را با env/کد مبدأ start کنید. بعد از دریافت دادهٔ جدید، مقصد را حفظ کنید و برای جلوگیری از دو شاخهٔ سوابق، قبل از rollback دامنهٔ رخدادهای جدید را reconcile کنید؛ داده‌ها خودکار merge یا دور ریخته نشوند. تغییر ظاهر فقط با حذف manifest آیکون و restart همان مقصد انجام می‌شود و نباید به rollback دیتابیس منجر شود.
