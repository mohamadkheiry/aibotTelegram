# ساختار ۹بخشی مدیریت و مسیر محصولات

مبنای پذیرش: درخواست مستقیم کاربر و PDF «توضیح امکانات ربات تلگرام الون اکانت»، صفحات ۱ تا ۳ برای ۹ بخش مدیریت و صفحه ۴ برای دو فرمت محصول. اصل PDF در [پوشه منابع](references/) بدون تغییر نگهداری شده است. این اصلاح، چیدمان ۱۳گروهی قبلی را جایگزین می‌کند؛ قابلیت‌های دامنه یا فرمان‌های سازگار حذف نشده‌اند.

## ۹ دکمه اصلی و محل زیرعملیات

| ترتیب | دکمه اصلی | محتوا |
|---|---|---|
| ۱ | مدیریت کلی ربات | وضعیت ربات، کارت، روش پرداخت، کانال و جوین اجباری، بکاپ مالک؛ زیرمنوهای مدیران/پشتیبان‌ها و دعوت/پاداش |
| ۲ | محصولات | دسته‌های اصلی ← زیردسته/محصول ← مشخصات، انبار، فرمت، نمایش/فروش، یادآوری و حذف |
| ۳ | سفارش‌ها | فهرست، جست‌وجو، جزئیات و عملیات سفارش؛ زیرمنوی پرداخت‌ها و بررسی فیش |
| ۴ | تیکت‌ها | فهرست، جست‌وجو، پیوست، پاسخ و وضعیت |
| ۵ | کاربران | جست‌وجو و فیلتر، جزئیات و تاریخچه‌ها، مسدودسازی، کیف پول و پیام |
| ۶ | ارسال پیام | پیام تکی، گروهی، خریداران محصول و زیرمجموعه‌ها؛ پیش‌نمایش شمارش‌شده ارسال گروهی |
| ۷ | سؤالات متداول | دسته‌ها، سوال‌ها، متن پاسخ، وضعیت و حذف |
| ۸ | تخفیف‌ها | فهرست، ایجاد، ویرایش، محدودیت‌ها و وضعیت کد |
| ۹ | گزارش | نوع گزارش، بازه و خروجی |

«منوی اصلی» دکمه خروج است، نه بخش دهم کسب‌وکار. owner/admin هر ۹ بخش را می‌بینند؛ support فقط سفارش‌ها، تیکت‌ها، کاربران و ارسال پیام را در حد مجوز فعلی دارد. نقش تازه‌ای ایجاد نشده است. رنگ و ترتیب منوی مشتری و نبود Unicode emoji در labelها حفظ شده‌اند.

## مسیر روزمره کالا

۱. «محصولات» فقط دسته‌های اصلی را نشان می‌دهد. وارد دسته شوید تا زیردسته‌ها و محصولات همان دسته را ببینید. دسته یا محصول مخفی با برچسب «مخفی» برای مدیر قابل مدیریت است؛ محصول حذف‌شده در فهرست نیست.

۲. «افزودن محصول در این دسته» و «افزودن زیردسته» والد فعلی را از قبل انتخاب می‌کنند. ویرایش نام/شرح/ترتیب/والد دسته و نمایش/حذف از همان دسته در دسترس است. حذف دسته دارای فرزند یا سابقه محصول رد می‌شود؛ حذف محصول soft-delete و بدون حذف سوابق سفارش است.

۳. محصول را باز کنید. خلاصه، نام و شناسه، مسیر دسته، قیمت و مدت، فرمت، نمایش، امکان خرید، رزرو و شمار موجودی را نشان می‌دهد. «اطلاعات و ویرایش محصول» مقدار کامل هر مشخصه را نمایش می‌دهد، سپس «ویرایش این مقدار» فرم همان محصول و همان مشخصه را باز می‌کند.

۴. مقدار جدید را وارد کنید و خلاصه را ببینید؛ تا «تأیید و اجرا» زده نشود داده تغییر نمی‌کند. «مرحله قبل / اصلاح» فقط پاسخ قابل ویرایش را برمی‌گرداند، نه محصول/مشخصه پیش‌انتخاب‌شده را. «لغو و بازگشت» اثر تازه‌ای ندارد.

۵. «بازگشت به بخش انتخاب‌شده» بعد از اجرا به محصول، دسته یا آیتم مربوط می‌رود. بازگشت محصول به دسته، صفحه/جست‌وجوی قبلی را حفظ می‌کند؛ اگر دسته محصول تغییر کرده باشد دسته جدید باز می‌شود. انبار و آیتم هم زمینه صفحه و جست‌وجوی خود را حفظ می‌کنند. پس از حذف، مقصد رکورد حذف‌شده نیست، بلکه والد معتبر است.

## ۲۳ مشخصه قابل مشاهده و ویرایش

نام، دسته، نوع تحویل، آیکون، توضیح کوتاه، توضیح کامل، قیمت به تومان، عنوان مدت، مدت به روز، نوع اکانت، روش فعال‌سازی، قابل تمدید، گارانتی، ویژگی‌ها، راهنمای فعال‌سازی، شرایط استفاده، قوانین، لینک قوانین، متن درخواست اطلاعات، متن تکمیل سفارش، راهنمای تحویل، روزهای یادآوری و سقف موجودی دستی.

متن کامل مشخصه بدون حذف انتها و با قطعه‌های امن Telegram نمایش داده می‌شود؛ keyboard در قطعه آخر است. متن HTML ذخیره‌شده در نمای «مقدار فعلی» به‌صورت source امن/escapeشده قابل مشاهده است. نمایش/عدم نمایش، موجود/ناموجود و رزرو کلیدهای جداگانه و تأییدشونده‌اند. داده‌های immutable مانند شناسه محصول، تاریخچه سفارش و آیتم تحویل‌شده «فیلد قابل ویرایش محصول» نیستند.

## انبار همان محصول

«انبار محصول» فقط آیتم‌های همان محصول را با شناسه و وضعیت نشان می‌دهد. هر صفحه ۲۰ رکورد، total دقیق، ترتیب ثابت و جست‌وجوی شناسه دارد. افزودن اکانت ready با «افزایش موجودی / افزودن اکانت» انجام می‌شود؛ محصول دوباره پرسیده نمی‌شود. کل payload ساختگی/واقعی مجاز را در یک پیام می‌فرستید و تأیید می‌کنید؛ محدودیت امن تحویل دامنه همچنان برقرار است.

آیتم تحویل‌نشده: ویرایش اطلاعات، حذف، فعال/غیرفعال‌کردن و در حالت آمادهٔ ready، تخصیص به کاربر. آیتم تحویل‌شده: مشاهده وضعیت، بدون ویرایش/حذف/تخصیص دوباره. تخصیص مستقیم همان order داخلی `admin_assignment` است و خرید تجاری یا درآمد نمی‌سازد؛ تقدم سفارش‌های پرداخت‌شده را هم دور نمی‌زند. payload محرمانه در فهرست، callback یا خلاصه تأیید بازنشر نمی‌شود.

## دو فرمت سند

| فرمت | رفتار و دکمه‌های مرتبط |
|---|---|
| موجود در انبار (`ready`؛ گزینه فرم «آماده و خودکار») | تحویل خودکار اکانت بعد از پرداخت؛ انبار واقعی، فعال/غیرفعال‌کردن رزرو، راهنمای تحویل |
| نیازمند اطلاعات کاربر (`manual`؛ گزینه فرم «فعال‌سازی دستی») | دریافت اطلاعات خریدار و تکمیل توسط مدیر؛ متن درخواست، متن تکمیل و سقف موجودی دستی |

انتخاب فرمت از صفحه خود محصول انجام می‌شود. manual به جای افزودن payload آماده، دکمه «تغییر سقف موجودی دستی» دارد؛ این مقدار سقف مطلق است، نه افزایش جمعی. قابلیت تازه‌ای برای قالب فایل یا تجزیه اجباری ایمیل/رمز/2FA اضافه نشده؛ چنین داده‌هایی می‌توانند متن payload ready باشند.

حفاظت موجود داده: ready دارای آیتم انبار، رزرو فعال یا سفارش آمادهٔ باز به manual تبدیل نمی‌شود. UI دلیل فارسی و راهنما می‌دهد و چیزی خودکار حذف نمی‌کند. برای محصول دارای سوابق تحویل، ساخت محصول manual جدا مسیر امن است. این guard قبلی دامنه حفظ شده، نه اینکه قواعد مالی در UI دوباره ساخته شوند.

| شناسه | مغایرت قبلی | اصلاح و شاهد |

| NAV-C02 | عملیات کلی محصولات به‌جای ورود به دسته و محصولات آن | درخت scoped، افزودن/ویرایش/وضعیت/حذف؛ تست‌های category tree، contextual add/delete |
| NAV-C03 | انتخاب دوباره محصول برای ویرایش مشخصه | ۲۳ نمای مقدار کامل و فرم با target/field ثابت؛ تست all fields و scoped correction؛ اجرای واقعی همه ۲۳ شاخه در navigation suite |

| NAV-C06 | بازگشت عمومی و گم‌شدن محل انتخاب | return_to، قفل target، حفظ دسته/انبار/صفحه/جست‌وجو و دسته جدید پس از انتقال؛ تست search/pagination/back و category change |

این عدد شمار موارد سامان‌دهی این انتشار است، نه ادعای شمارش همه باگ‌های احتمالی سامانه.

## قرارداد Agent و آزمون پذیرش

- `admin_catalog.py` مرور خواندنی و بازکردن فرم است؛ query mutation تازه در controller ندارد.
- `admin:catalog` با ID پایدار مرور می‌کند؛ `admin:ui` همچنان token/revision، role زنده، journal و تأیید دارد. `minimum_step` و `return_to` اختیاری‌اند و state قدیمی قابل ادامه است.
- بازنشسته‌کردن markup پیام best effort است. ID مرور حتی اگر قدیمی باشد فقط صفحه/فرمِ همان موجودیت را باز می‌کند؛ هیچ callback مرور بدون تأیید اثر دامنه ندارد. تأیید قدیمی فرم فقط UI فعلی را بازیابی می‌کند.
- آزمون‌ها از keyboard و message ID خروجی FakeTelegram استفاده می‌کنند. جعل فقط در تست منفی تعمدی است. دیتابیس‌ها موقت‌اند؛ هیچ خرید، پیام آزمایشی مشتری یا getUpdates دوم ایجاد نمی‌شود.

```bash
python -m unittest tests.test_admin_catalog_hierarchy tests.test_admin_ui_navigation tests.test_admin_buttons -v
python -m unittest discover -s tests -v
python -m ruff check .
python -m compileall -q app tests
```

نتیجه محلی 2026-09-05: مجموعه کامل ۳۶۶ تست در Windows/Python 3.14 اجرا شد؛ ۳۶۴ موفق، ۲ تست مخصوص POSIX طبق انتظار skip و صفر failure/error. ۲۱ تست اختصاصی جدید موفق‌اند: مجوز خصوصی، تغییر نقش هنگام تأیید، callback جعلی/cross-product، restart، crash پس از ثبت پیام، stale فرم و تأیید تکراری نیز پوشش دارند. بعد از کوتاه‌سازی صرفاً نمایشی عنوان زمینه، تست متن بلند نیز جداگانه دوباره موفق شد و نام اصلی دست‌نخورده ماند. Ruff، compile، سلامت اسناد/لینک‌ها/منابع و secret scan موفق‌اند. CI لینوکس همان release پیش از rollout باید سبز باشد و نتیجهٔ دقیق آن در Checks گیت ثبت می‌شود.

سه نمودار قبلی و نمودار تازه ۱۷ رندر و از نظر متن/چیدمان بررسی شدند. آموزش مدیریت با مسیر جدید بازتولید شد: MP4 بی‌صدا، ۱۹۲۰×۱۰۸۰، ۱۷۱ ثانیه؛ کنترل بیرون‌زدگی تمام اسلایدها، بازبینی فریم‌های تغییرکرده، decode کامل و پخش مرورگری موفق بود. آموزش استقرار تغییر باینری نکرد. این پوشش، آزمون تصویری کلاینت‌های واقعی Telegram یا تضمین نبود هر باگ احتمالی نیست.
