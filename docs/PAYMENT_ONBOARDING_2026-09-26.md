# پیگیری اتصال پرداخت — ۲۰۲۶-۰۹-۲۶

این سند نتیجه بررسی پیام‌های تازه کارفرما و کد است، نه گزارش انتشار یا تکمیل پرداخت زنده. متن خام گفت‌وگو، اطلاعات شخصی و مالی پیامک، کلید و رمز در مخزن ثبت نشده‌اند. نسخه اجرایی همان [انتشار جاری](CURRENT_DEPLOYMENT.md) است.

## پاسخ‌های دریافت‌شده و تطبیق با سند

- بانک مقصد بلو است و گوشی اندرویدی همیشه‌روشن در اختیار کارفرماست؛ یک نمونه متن واریز دریافت شد. مشخص نیست متن از SMS است یا notification برنامه بانک؛ sender/package و نصب MacroDroid هنوز تأیید نشده‌اند.
- سرویس ارزی مدنظر کارفرما **IR Crypto Pay** است، نه Plisio. مشکل دریافت ایمیل ورود/ثبت‌نام گزارش شده؛ رفع مشکل و دسترسی به کلید هنوز تأیید نشده است.
- کارفرما استفاده از دامنه سایت خود را مطرح کرده؛ نام دامنه و مسئول DNS هنوز مشخص نیست.
- سند اولیه پرداخت خودکار کارت با MacroDroid و پرداخت ارزی با API «Plisio یا موارد مشابه» را خواسته است: `references/requirements-pdf-1.txt` خطوط ۱۱۱ تا ۱۱۳ و `requirements-pdf-2.txt` خطوط ۶۹ تا ۷۰. این دو قابلیت و انتخاب سرویس مشابه را خارج از سند معرفی نکنید.

## رفع ابهام دامنه

ربات همچنان فقط با یک `getUpdates` اجرا می‌شود؛ برای دریافت update تلگرام دامنه یا webhook لازم ندارد. callback کارت سرویس جداگانه‌ای است و ارتباط اینترنتی گوشی با آن باید احراز‌شده و امن باشد. زیردامنه سایت موجود می‌تواند استفاده شود، مشروط به تنظیم DNS، گواهی معتبر و مسیر دسترسی عمومی به reverse proxy. آدرس خصوصی `192.168.10.111` به‌تنهایی از اینترنت گوشی قابل دسترسی نیست؛ صرف افزودن رکورد DNS به این IP مسئله را حل نمی‌کند. پیش از هر exposure، مسیر شبکه و محدوده مجاز بررسی شود؛ سایر سرویس‌های میزبان نباید باز یا تغییر داده شوند.

## بلو: آماده‌سازی بدون ادعای اتصال زنده

کد فعلی `/payments/card/confirm`، JSON شامل عدد صحیح تومان، `reference` پایدار و `occurred_at` دارای timezone می‌پذیرد؛ متن خام SMS را parse نمی‌کند. [قرارداد فعلی و راهنمای MacroDroid](DEPLOYMENT_FA.md) مبناست.

1. مبدا واقعی را مشخص کنید: SMS و sender معتبر یا notification و package بانک. پیام کاربر، اسکرین‌شات فیش یا forward دستی سند پرداخت خودکار نیست.
2. از قالب واریز بانک فقط مبلغ واریز را بگیرید، نه موجودی حساب. ارقام فارسی/عربی و جداکننده‌ها normalize شوند. ریال به تومان دقیق تبدیل شود؛ باقیمانده غیرقابل تبدیل را گرد نکنید.
3. نمونه موجود شماره پیگیری بانکی ندارد و زمان نمایشی آن دقیقه‌ای است. شیوه ثبت شناسه پایدار پیام/رخداد، دقت زمان و تأخیر رسیدن باید روی دستگاه روشن شود. هر retry باید همان شناسه و زمان را حفظ کند؛ زمان ارسال HTTP یا شناسه تصادفی تازه جای هویت رخداد نیست. صرف hash مبلغ و ساعت دقیقه‌ای نیز یکتایی دو واریز را تضمین نمی‌کند.
4. secret فقط در header و در تنظیم امن گوشی/سرور باشد؛ در چت، URL یا لاگ ثبت نشود. HTTPS عمومی یا مسیر خصوصی امن باید واقعاً از گوشی آزمایش شود.
5. تست نهایی با هماهنگی مالک شامل مبلغ دقیق، تبدیل واحد، دوباره‌ارسالی، قطعی/تأخیر گوشی، رخداد قدیمی، مبلغ اشتباه و دو رخداد مشابه است. تست‌های مصنوعی جای این آزمایش را نمی‌گیرند.

## IR Crypto: قرارداد عمومی و فاصله با کد موجود

مرجع بررسی‌شده در این تاریخ: [مستندات رسمی API](https://ircryptopay.online/docs). این بررسی تأیید اعتبار مالی سرویس یا حساب پذیرنده نیست.

- ساخت فاکتور: `POST /v1/invoices`، کلید در Bearer header، مبلغ رشته‌ای و شناسه `external_ref` برای retry همان فاکتور.
- استعلام: `GET /v1/invoices/{id}`؛ بنابراین اتصال مبتنی بر polling وضعیت، بدون webhook ورودی، از نظر قرارداد عمومی ممکن است.
- مبلغ پایه فروشگاه تومان است؛ درخواست ریالی باید تبدیل دقیق ×۱۰ داشته باشد. هویت فاکتور، `external_ref`، مبلغ و واحد باید پیش از هر settlement تطبیق داده شوند.
- کد فعلی `app/plisio.py` و مسیرهای orchestration/evidence در `app/bot.py` برای قرارداد Plisio هستند. واردکردن کلید IR Crypto در `PLISIO_API_KEY` یا تغییر URL به‌تنهایی اتصال صحیح ایجاد نمی‌کند.
- adapter مستقل، انتخاب/ثبت هویت provider برای هر intent، حفظ invoiceهای قبلی، تطبیق وضعیت‌ها، durable evidence و recovery باید پیاده و تست شوند. API key نباید در خطا یا log نشت کند. هیچ fallback خودکار به provider دیگر مجاز نیست.
- مستندات عمومی نمونه کامل تسویه دارای مبلغ دریافتی و رفتار اضافه‌واریزی/پرداخت ناقص پس از expiry را روشن نمی‌کنند. قبل از فعال‌سازی، با حساب تست/پاسخ رسمی سرویس بررسی شود. وضعیت expired یا canceled به‌تنهایی شاهد دریافت صفر نیست؛ ابهام باید review شود، نه اینکه اعتبار یا failure قطعی ساخته شود. سیاست مبلغ متفاوت کارت را بدون قرارداد ارزی به crypto تعمیم ندهید.

## موارد در انتظار پاسخ/دسترسی

| مورد | اقدام بعدی |
|---|---|
| نوع پیام بلو، sender/package و نصب MacroDroid | پاسخ کارفرما و بررسی تنظیم واقعی گوشی |
| نام دامنه و مسئول DNS | هماهنگی مسیر HTTPS و دسترسی شبکه؛ بدون درخواست رمز در چت |
| مشکل ایمیل IR Crypto و آماده‌بودن حساب | پیگیری کارفرما با سرویس، سپس تنظیم کلید در محیط امن |
| قرارداد واقعی حالات paid/partial/expired و مبالغ | پاسخ رسمی یا fixture سانسورشده حساب تست؛ بدون حدس مالی |
| زمان تحویل نهایی | اعلام پس از مشخص‌شدن دسترسی‌ها و دامنه تست زنده؛ وعده تکمیل یا موعد قطعی بدون این شواهد ندهید |

## شاهد این بررسی

`python -m unittest tests.test_payment_server tests.test_plisio -q`: **۱۷ تست، ۰٫۹۹۹ ثانیه، OK** در محیط QA محلی. این تست‌ها پایه callback و adapter موجود Plisio را می‌سنجند؛ آزمون اتصال بلو یا IR Crypto و تأیید سلامت سرویس زنده نیستند. این پیگیری فقط مستنداتی است؛ روش پرداخت، تنظیمات production، schema و داده‌های مالی تغییر نکرده‌اند.
